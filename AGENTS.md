# Правила работы с репозиторием

## Полномочия и внешние действия

- Все планы, спецификации, код, результаты проверок и артефакты по умолчанию
  остаются на локальной машине.
- Не создавать коммиты и не делать push без отдельного прямого разрешения
  пользователя именно на это действие.
- Не создавать и не изменять PR, комментарии, reviews, issues, сообщения и другие
  внешние коммуникации без отдельного прямого разрешения пользователя.
- Не загружать, не публиковать и не прикреплять материалы к внешним сервисам
  без отдельного прямого разрешения пользователя.
- Перед таким действием назвать точное действие и назначение и дождаться
  явного подтверждения. Молчание, общее поручение реализовать задачу или разрешение
  на другое действие не являются подтверждением.
- Работа над интеграцией не разрешает агенту менять данные живого Keitaro:
  проверка записи требует отдельного разрешения с указанием тестовых объектов.
- Не выводить секреты в логи, ответы, документы, команды или Git. Доступы находятся
  в игнорируемом `.local/secrets/`; настройки приложения будут поступать из окружения.

## Документы и порядок работы

- Актуальная основа требований — `docs/specs/000-requirements.md`.
- Требования из исходного задания и принятые нами решения различать явно.
- Спецификации хранить в `docs/specs/`, иллюстрации — в `docs/assets/`.
- Дизайн и продуктовый контекст — `docs/design/DESIGN.md` и
  `docs/design/PRODUCT.md`; инструкции запуска и работы — `docs/guides/`.
  Навигация — `docs/README.md`. В корневом README оставлять только краткое
  описание, быстрый запуск и ссылки; не создавать дополнительные документы в корне.
- Dockerfile хранить в `deploy/`; Compose и конфиги инструментов оставлять
  в корне для стандартных команд. Локальные кеши — `.local/cache/`.
  `.impeccable/`, `.claude/`, `.agents/`, `.codex/` и `.local/` не включать в Git.
- Планы хранить только в игнорируемом `docs/plans/`; не включать их в коммиты.
- Спецификация описывает поведение, контракты, ограничения и решения.
  Конкретные шаги реализации, тела методов и команды относятся к плану.
- Не дублировать продуктовые правила: техническая спецификация ссылается
  на соответствующее правило ТЗ и уточняет его реализацию.
- Техническая спецификация — `docs/specs/002-technical-design.md`, контракт
  интеграции и проверки совместимости — `docs/specs/001-keitaro-contract.md`.
  Локальный план — `docs/plans/001-implementation-plan.md`.
- Локальная реализация, миграции и тесты подготовлены. K-01/K-03/K-05 подтверждены
  на Keitaro 11.5.0; создание, Push и конфликт проверены на отдельной кампании.
  Фактический геопереход и обрыв живой записи остаются вне проверки;
  границы K-02/K-04 описаны в `docs/guides/validation.md`.
- Проверять фактический API до фиксации его контрактов; не представлять
  неподтверждённые предположения о Keitaro как установленные факты.

## Backend

- FastAPI — на границе приложения. Домен не зависит от FastAPI, ORM,
  HTTP-клиентов, Pydantic и DI-контейнера.
- `domain/` хранит сущности и инварианты; `application/` — use cases, DTO,
  порты и исполнение команд; `infrastructure/` — адаптеры. `bootstrap/` собирает
  зависимости, `main.py` создаёт приложение. Внутренние слои не импортируют внешние.
- Предметные модули `campaigns`, `streams`, `offers`, `operations` группируют
  связанный код. Не возвращать общий плоский каталог всех use cases или handlers.
- В `api/v1/<module>/` разделять `handlers.py`, `schemas.py`, `depends.py`.
  In/Out-схемы описывают HTTP-контракт; JSON endpoints имеют `response_model`.
  Application DTO — dataclasses без зависимости от Pydantic.
- Dependencies выдают конкретный use case или executor; handlers не получают
  контейнер, ORM session или transaction. Пагинация использует общие
  `Pagination`, `Page[T]`, `PaginationIn`, `PageOut[T]`.
- Сущности и value objects отвечают за инварианты; use cases координируют работу
  через порты. Реализации доступа к данным и внешним системам — адаптеры.
- Порт Keitaro возвращает типизированные DTO. Внешний JSON собирают и разбирают
  только адаптеры; domain/application передают Snapshot как непрозрачное значение.
- Репозитории campaigns, streams, operations и catalog объединены Unit of Work
  одной транзакции. Не возвращать универсальный IStore со всеми методами.
- Переходы и повторный запуск операции проверяет сама сущность. Время передаётся
  в доменные методы явно; application получает IClock через composition root.
- Проекции для интерфейса формирует application; сериализацию снимков для БД —
  persistence. Домен не строит словари HTTP/ORM-представлений.
- Команда и результат use case располагаются рядом с ним; зависимости внедряются
  явно. Транзакционные границы принадлежат use case.
- Handler выполняет валидацию и mapping, вызывает use case и переводит ошибки
  в HTTP-контракт; бизнес-логику в handler не размещать.
- Не использовать `__init__.py` для реэкспорта. Импорты размещать в начале файла.
- Изменения сущности выполнять через доменные методы, а не снаружи через поля.
- Аннотировать входы и результаты функций; соблюдать порядок методов интерфейса
  в реализации. Не рефакторить несвязанный с задачей код.
- Если параметры или аргументы переносятся на несколько строк, ставить
  завершающую запятую и запускать formatter: каждый параметр на отдельной строке.
- Уже применённые миграции не редактировать. Автогенерацию проверять вручную.
  Миграции рабочей БД запускает пользователь; тесты работают с изолированной БД.

## Проверки

- Домен проверять по результатам и публичному состоянию без БД и моков.
- Хранение и use cases проверять с реальной тестовой PostgreSQL и миграциями;
  внешние системы заменять на границе интеграции.
- HTTP-адаптеры проверять по запросам, ответам и ошибкам; API — по транспортным
  контрактам, не дублируя доменные тесты.
- Не включать обращения с записью в живой Keitaro в обычный запуск тестов.
- Для изменений только документации проверять ссылки, согласованность,
  отсутствие секретов и правила игнорирования; тесты приложения не требуются.
