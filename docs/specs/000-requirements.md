# ТЗ: обёртка над Keitaro

Статус: основа для технической спецификации и плана реализации.
Дата: 18 ноября 2026 года.

Документ объединяет два предоставленных описания задания, четыре скриншота
и расшифровку демонстрации редактора. Раздел «Исходные требования» отражает
задание; раздел «Принятые решения» закрывает неоднозначности по поручению
владельца репозитория. Продуктовые решения не являются утверждениями о
возможностях конкретной версии API — их совместимость подлежит проверке.

## 1. Цель и границы

Создать приложение, которое создаёт рекламные кампании в Keitaro и позволяет
управлять офферами в их потоках через локальный редактор с явной публикацией.
Приоритет — корректность состояния, весов и синхронизации.

Первый выпуск работает с одним экземпляром Keitaro. Он содержит создатель
кампаний, редактор потоков, поиск офферов и необходимую локальную БД.
Полноценный интерфейс управления Keitaro, аналитические отчёты, управление
пользователями и автоматическая фоновая синхронизация в объём не входят.

## 2. Термины

| Термин | Значение |
| --- | --- |
| Кампания | Объект Keitaro с доменом, группой, источником и потоками |
| Поток | Правило маршрутизации внутри кампании |
| Оффер | Самостоятельный объект Keitaro, на который направляется трафик |
| Привязка | Участие оффера в конкретном потоке; удаление привязки не удаляет оффер |
| Базовое состояние | Последнее успешно полученное или подтверждённо опубликованное состояние |
| Черновик | Текущее локальное состояние, отличающееся от базового |
| Архив | Известные приложению привязки, отсутствующие в опубликованном составе потока |
| Закрепление | Локальное правило сохранять заданный вес при перераспределении |
| Конфликт | Изменение потока в Keitaro после получения базового состояния |

## 3. Исходные требования

### R-01. Создание кампании

Ввод: название кампании, геокод страны и ID оффера Keitaro.
Оффер можно выбирать через поиск с автодополнением.

Результат — кампания с настроенными доменом, группой и источником и двумя потоками:

1. Первый поток принимает посетителей из указанной страны и перенаправляет
   на `https://google.com`.
2. Второй поток принимает остальных посетителей и направляет на выбранный оффер.

Порядок потоков существенен: первый подходящий поток определяет маршрутизацию.
Для тестовых кампаний требуется префикс `test_<фамилия>_`.

### R-02. Получение потоков

`Fetch Streams` получает потоки существующей кампании и их офферы.
Поток без офферов отображается как поток без разбора фильтров, URL редиректа
и прочих настроек его содержимого.

### R-03. Локальное редактирование и публикация

- Добавление оффера меняет локальный состав и пересчитывает веса.
- Изменённый поток получает видимый признак неопубликованных изменений.
- До `Push to KT` состав в Keitaro остаётся прежним.
- `Push to KT` публикует изменения выбранного потока.
- `Cancel` отменяет неопубликованные изменения; новые привязки, ещё не попавшие
  в опубликованное состояние, не остаются в локальной базе как архив.

### R-04. Удаление и восстановление

- `Remove` делает привязку неактивной, отображает её серой с долей 0% и меняет
  локальное состояние потока.
- После публикации оффер отсутствует в потоке Keitaro, но привязка остаётся
  в локальном архиве с действием `Bring Back`.
- Восстановление возвращает привязку в локальный активный состав; публикация
  возвращает её в Keitaro.
- Если оффер удалили из потока непосредственно в Keitaro, повторный Fetch
  переводит известную приложению привязку в архив вместо её полного удаления.

### R-05. Веса

- Без закреплений активные офферы делят трафик поровну с учётом округления.
- Закреплённые веса не меняются при добавлении, удалении и восстановлении
  остальных офферов.
- Остаток после закреплённых долей распределяется между незакреплёнными.
- Общая доля активных офферов после перерасчёта составляет 100%.

### R-06. Технологии и сдача

Обязательны FastAPI и SQLAlchemy; frontend выбирается свободно.
Результат должен включать понятный README с миграциями и запуском.
В исходном задании указан срок пять дней, но дата начала отсчёта не задана.
Способ сдачи — ссылка на GitHub; фактическая публикация выполняется только
после отдельного разрешения владельца репозитория.

## 4. Принятые решения

### D-01. Объём интерфейса и хранения

- Один экземпляр Keitaro и одно общее состояние редактора; персональных
  черновиков и совместного редактирования в реальном времени нет.
- Черновики, архив, закрепления и базовое состояние сохраняются в PostgreSQL
  и переживают перезагрузку страницы и перезапуск приложения.
- Кампания открывается по ID; ранее импортированные кампании доступны в локальном
  списке. Загружать весь каталог кампаний для начала работы не требуется.
- Поиск офферов выполняется через backend по ID или названию в Keitaro.
  Название не является идентификатором; результаты показывают и ID, и название.
- Базовая поставка предназначена для локального запуска с доступом через loopback.
  Собственная система учётных записей не добавляется. Публичное развёртывание
  требует отдельного решения об аутентификации и защите доступа.

### D-02. Создание и настройки по умолчанию

- Домен, группа, источник и префикс тестовых кампаний задаются конфигурацией.
  В форме создания достаточно названия, одной страны и одного оффера.
- Используются существующие объекты Keitaro; приложение не создаёт домены,
  группы, источники или сами офферы.
- Перед созданием проверяются обязательные настройки и доступность выбранных
  объектов. Не подставлять случайный первый домен или группу при ошибке настройки.
- Геокод — одна страна в формате ISO 3166-1 alpha-2. Ввод нормализуется в верхний
  регистр и проверяется по справочнику. Перечень кодов на макете трактуется
  как примеры выбора, а не запрос на несколько стран сразу.
- Настроенный префикс добавляется ровно один раз; пустое название отклоняется.
  Конкретную фамилию задаёт оператор конфигурацией, она не зашивается в код.
- Во втором потоке начальный оффер получает 100%. После полного успеха
  показываются ID кампании, её ссылка и переход к редактору.
- Кампания создаётся выключенной и включается только после проверки обоих
  потоков; частично созданная кампания не должна принимать трафик.
- Создание сразу обращается к Keitaro; у создателя нет отдельного этапа Push.

### D-03. Границы редактирования

- Действия редактора применяются к одному потоку. Push и Cancel также относятся
  к одному потоку; массовая публикация не требуется.
- Изменяются только состав и веса офферов. Фильтры, порядок потоков, режим
  маршрутизации, лендинги, редиректы и остальные настройки сохраняются.
- Произвольный поток без офферов отображается только для чтения. Превращать
  редиректный поток в поток офферов редактор не умеет.
- Если известный поток офферов опустел в Keitaro, его прежние привязки сохраняются
  в архиве. Восстановление допустимо только если поток всё ещё поддерживает офферы;
  при смене его типа или действия поток становится доступным только для чтения.
- Если поток исчез из Keitaro, он отмечается как недоступный. Локальная история
  сохраняется, но Push не создаёт замену исчезнувшему потоку.
- Оффер с одним ID может быть активен только один раз в данном потоке. Повторное
  добавление архивного оффера эквивалентно Bring Back; активного — отклоняется.
- Remove никогда не удаляет объект оффера из Keitaro. Для ещё не опубликованной
  новой привязки Remove просто убирает её из черновика без создания архива.
- Последний активный оффер через редактор удалять нельзя. Если поток пришёл
  пустым извне, его можно восстановить до допустимого непустого состава.
- Восстановление или публикация оффера, больше не доступного в Keitaro,
  завершается понятной ошибкой без потери локального черновика.

### D-04. Закрепление и распределение весов

- В интерфейсе вес задаётся целыми процентами. Для закрепления доступны текущий
  рассчитанный вес и ручной ввод целого значения от 1 до 100.
- Закрепление — локальная метаинформация; в Keitaro отправляются только итоговые
  веса и состав. Изменение закрепления входит в черновик и отменяется через Cancel.
- После добавления, Remove, Bring Back, закрепления, изменения закреплённого
  значения или снятия закрепления выполняется один и тот же перерасчёт.
- Пусть сумма закреплённых весов равна P, а число незакреплённых офферов равно N.
  При N > 0 каждый получает целую часть (100 − P) / N. Оставшиеся процентные пункты
  выдаются по одному в порядке возрастания ID оффера. Это даёт стабильный результат.
- Любая локальная операция должна оставлять каждому активному офферу хотя бы 1%.
  Если остатка недостаточно, операция целиком отклоняется с объяснением причины.
- При N = 0 допустима только сумма закреплений 100%. Переполнение и незаполненный
  остаток блокируют изменение; закреплённые значения автоматически не исправляются.
- Удаление закреплённой привязки снимает её закрепление в черновике. При Bring Back
  она возвращается незакреплённой. Cancel восстанавливает прежнее закрепление.
- Вес архивной или помеченной к удалению привязки — 0%; она не участвует в расчёте.
- Fetch сохраняет фактические веса Keitaro, включая неравномерные; не выравнивает
  их автоматически. Внешний активный оффер с весом 0 остаётся активным и явно
  отличается в интерфейсе от Removed. Первая локальная операция приводит состав
  к указанным выше правилам либо отклоняется, если это невозможно.
- Не поддерживаемые редактором значения или режимы распределения отображаются
  с причиной недоступности редактирования, без скрытого округления и перезаписи.
- Отключённая привязка Keitaro не равна удалённой привязке нашего архива.
  В первом выпуске потоки с отключёнными или неизвестными состояниями привязок
  доступны только для чтения; редактор не включает их и не удаляет молча.

Примеры результата перерасчёта:

| Активный состав | Результат в порядке возрастания ID |
| --- | --- |
| Три оффера без закреплений | 34%, 33%, 33% |
| Четыре оффера без закреплений | 25%, 25%, 25%, 25% |
| Первый закреплён на 25%, ещё два свободны | 25%, 38%, 37% |
| Один оффер без закрепления | 100% |
| Один закреплён на 100%, добавляется второй | Отклонение: для второго нет доли |
| Удаление свободного оффера оставляет только закреплённый на 25% | Отклонение: остаток некому распределить |

### D-05. Cancel и признак изменений

- Cancel полностью возвращает поток к последнему успешному Fetch или Push:
  состав, веса, архив и закрепления. Сетевой запрос на запись не выполняется.
- Изменённость определяется сравнением с базовым состоянием. Обратная операция,
  полностью восстановившая базовое состояние, снимает признак изменений.
- Архив, существовавший до начала редактирования, сохраняется после Cancel.
- Нельзя отменить уже опубликованную запись в Keitaro кнопкой Cancel.

### D-06. Fetch и внешние изменения

- Fetch импортирует всю выбранную кампанию. Если хотя бы в одном её потоке есть
  черновик, Fetch блокируется до Push или Cancel соответствующих потоков.
- Успешный Fetch принимает внешний состав и веса как новую базу. Новые привязки
  становятся активными, исчезнувшие известные привязки переходят в архив.
- Уже архивные привязки не исчезают при последующих Fetch. Если они снова появились
  в Keitaro, они возвращаются в активный состав без дублирования.
- Для оставшихся активными привязок признак закрепления сохраняется; закреплённым
  значением становится актуальный внешний вес. При недопустимом для закрепления
  значении закрепление снимается с явным уведомлением. Исчезнувшие привязки
  теряют закрепление; вновь обнаруженные изначально не закреплены.
- Локальное принятие результата Fetch атомарно: ошибка получения части потоков
  не оставляет кампанию наполовину обновлённой.
- Fetch не выполняет записей в Keitaro. После успеха обновлённые потоки не имеют
  неопубликованных изменений.

### D-07. Push, конфликты и неопределённый результат

- Перед Push приложение перечитывает поток и сравнивает его значимое состояние
  с базовым: состав, веса и настройки маршрутизации. Статистика и другие
  изменяющиеся служебные поля сами по себе не создают конфликт.
- Если поток изменён извне или удалён, публикация блокируется. Черновик сохраняется.
  Автоматического слияния и принудительной перезаписи нет. Пользователь может
  сделать Cancel, затем Fetch и применить изменения повторно.
- При успехе проверяется фактический результат в Keitaro; только подтверждённое
  состояние становится новой базой. Локальные архивные привязки сохраняются.
- Изменения только закреплений могут быть подтверждены локально после проверки
  актуальности удалённого состояния; лишний запрос записи не нужен.
- Ошибка до записи сохраняет черновик и позволяет повторить операцию.
- Timeout после отправки записи означает неопределённый результат, а не доказанный
  отказ. Поток блокируется для последующих изменений до чтения фактического
  состояния: совпадение с ожидаемым завершает Push; совпадение с прежним позволяет
  повтор после завершения прежнего запроса; иное состояние трактуется как конфликт.
- До разрешения неопределённого результата Cancel не должен создавать иллюзию,
  что удалённая запись отменена. Если завершение запроса нельзя подтвердить,
  сохраняется блокировка и требуется ручная сверка.
- Ручное разрешение — отдельное подтверждаемое действие после проверки оператором
  завершения запроса. Принятие текущего внешнего состояния явно сбрасывает
  черновик; это не скрытый Cancel. Частично созданная кампания остаётся неполной
  до проверки всех шагов и активации.
- Проверка перед записью уменьшает риск конфликта, но сама по себе не обеспечивает
  атомарность между чтением и записью. Наличие условной записи или версий в API
  проверяется отдельно; при их отсутствии это ограничение явно документируется.

### D-08. Частичное создание и повторные действия

- Создание кампании и её потоков может потребовать нескольких внешних запросов.
  Ошибка промежуточного шага не считается успешным созданием.
- Сохраняются известные ID и статус незавершённой операции; интерфейс сообщает,
  что создано и какой шаг не завершён. Повтор продолжает известную операцию,
  а не безусловно создаёт новую кампанию.
- При неопределённом результате создания сначала выполняется сверка. Если API
  не позволяет однозначно найти результат, автоматический повтор блокируется
  и показывается необходимость ручной проверки.
- Автоматически удалять частично созданную кампанию в качестве компенсации
  не нужно; неудача не должна запускать дополнительные разрушительные действия.
- Повторный клик не создаёт параллельную публикацию или создание. Устаревшая
  версия черновика из другой вкладки отклоняется, не затирая более новые изменения.

### D-09. Интерфейс и наблюдаемость

- Различать состояния: синхронизирован, изменён, публикация выполняется,
  конфликт, результат требует проверки и недоступен.
- Для привязок различать активную, новую, помеченную к удалению и архивную.
- Помимо цвета использовать подписи; показывать ID, название, процент и закрепление.
- В потоке показывать сумму активных весов и доступность действий.
- Сетевые ошибки, недоступные офферы, конфликт и нарушение весов имеют разные
  понятные сообщения. Не показывать пользователю необработанные трассировки.
- API-ключ доступен только backend; он не попадает в HTML, JavaScript или логи.

### D-10. Техническое направление

- Backend: async FastAPI, SQLAlchemy, PostgreSQL, Alembic; HTTP-интеграция через httpx.
- Домен отделён от транспорта и хранения; бизнес-инварианты находятся в сущностях
  и value objects, оркестрация — в use cases, интеграция — в адаптерах портов.
- Frontend: серверные шаблоны Jinja2 и небольшой JavaScript для интерактивности.
  Отдельный SPA, сборка Node.js и frontend-фреймворк не требуются.
- Для воспроизводимого локального запуска предусмотреть Docker Compose.
  Отдельный брокер, worker и Redis в первом выпуске не нужны.
- Конкретные версии, структура таблиц, HTTP-контракты нашего приложения,
  транзакционные границы и механизм повторов определяются технической спецификацией.

## 5. Критерии приёмки

| ID | Проверяемый результат |
| --- | --- |
| A-01 | Валидный ввод создаёт кампанию с настроенными доменом, группой, источником, префиксом и двумя потоками в нужном порядке |
| A-02 | Геопоток перенаправляет выбранную страну на Google, fallback-поток содержит выбранный оффер с весом 100% |
| A-03 | Импорт показывает потоки и фактические офферы/веса; редиректные потоки доступны только для чтения |
| A-04 | Add, Remove, Bring Back и закрепления сохраняются после перезагрузки страницы, но не меняют Keitaro до Push |
| A-05 | Перерасчёт соответствует D-04, даёт 100%, сохраняет закрепления и стабильно распределяет округление |
| A-06 | Недопустимая операция с весами или последним оффером отклоняется целиком, без частичного изменения черновика |

| A-11 | Fetch при черновике и Push при внешнем конфликте не затирают изменения; пользователь получает объяснение |

## 6. Проверка интеграции

Это техническая проверка интеграции, а не открытые продуктовые вопросы.
Публичная схема исследована. Результаты и оставшиеся проверки K-01–K-05
зафиксированы в [контракте Keitaro](001-keitaro-contract.md).
Авторизованный доступ к экземпляру пока не проверен: админка отвечает 403,
API без ключа — 401. Разработка не должна выдавать публичную схему за проверку
конкретного экземпляра.

- Версия и доступная схема Admin API: аутентификация, ошибки, пагинация,
  поиск офферов, домены, группы и источники.
- Формат создания кампании, геофильтра и fallback-потока; настройка порядка
  обработки, редиректа, домена и источника.
- Представление офферов, единицы и допустимые значения весов, возможная
  нормализация сервером и поддерживаемые режимы маршрутизации.
- Способ обновления состава потока без изменения остальных настроек,
  включая сохранение неизвестных адаптеру полей при необходимости полного update.
- Возможность условной записи, определения версии и безопасного распознавания
  результата после timeout; доступность чтения сразу после записи.
- Ограничения прав тестового аккаунта. Исследование начинается с чтения;
  запись в живой экземпляр агент выполняет только после отдельного разрешения.

Если фактический API расходится с принятым продуктовым контрактом, в технической
спецификации нужно явно зафиксировать совместимый вариант и обновить это ТЗ,
а не скрывать отличие в реализации.
